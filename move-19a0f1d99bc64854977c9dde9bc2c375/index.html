What the whole migration is actually for.

This move is for three things, and making the current code run faster is none of them: one trustworthy foundation of data that every part of Axiom3D drinks from, a way to describe a trading idea in ordinary words and get back a safe, repeatable experiment, and answers plain enough to act on without reading a single line of code. Everything else on this page — how data is captured, where it is stored, how experiments run, how risk is tested, how the machine is watched, what server all of it needs — follows from that one idea.

01

Overview

This is not a two-day rewrite of one scraper or one viewer.

It is the design of a whole-system move. It covers how live data is captured, where the engine's boundaries sit, how data is stored once and shared by everything, how research is run, how scheduled work is born and how it dies, how AI is allowed to help, how risk and execution are tested honestly, how the machine is watched and secured, how new parts get added later, and what server all of that adds up to.

Phanes and the viewers are one module inside that rather than the project itself. Olympus is deliberately later, and it is not allowed to block either the migration or the server purchase.

Read this page in two halvesAlmost everything below is target design: the rules the moved system must obey once it exists. It describes what is being built toward, not what is running today.

The one section that describes reality right now is Where the work stands. Nothing on this page claims to be finished unless that section says it is.

  • The live system is untouched. Nothing here has been switched on, switched off, or rewired on the machine you use today.
  • Nothing runs with real money. Every position discussed on this page is a paper position — a simulation used to measure whether an idea would have worked.
  • The server decision comes last, once the design has survived independent review.

02

Status

Where the work stands.

Every step below is labelled in plain words, without percentages or invented dates, so this reads as the honest position at this checkpoint.

  1. Done

    The review-and-evidence machinery is built

    There is now a dependable way to run an independent review of the whole architecture and keep its answer as evidence. The recovered independent review is preserved and fully replay-verified — it can be re-read and re-checked from stored evidence rather than re-run from scratch. Future reviews are pinned to the correct installed model generation, without breaking or invalidating the evidence already held.

  2. In progress

    Feeding that review into the official record

    Wiring the recovered review into the canonical migration ledger — the single official record of what was found, what was decided and why — and proving that the next review can read that ledger as an input rather than starting blind.

  3. Next

    Apply the findings and the requirements on this page

    Five architecture findings are already on the table and must be repaired. Alongside them go the requirements described here: the human-first Lab, the full life-and-death cycle for scheduled work, shared data instead of copies, honest timing and risk testing, and controlled concurrency so heavy research cannot crowd out the fast path.

  4. Then

    Attack the whole architecture again, repeatedly

    Run independent whole-architecture reviews against unchanged evidence, over and over, until no new material blocker appears. If a review finds a genuine problem, it gets fixed and the count starts again. A finding is never waived to protect a schedule.

  5. Handoff

    Freeze the server package

    Verify and freeze the capacity model and machine specification, the step-by-step migration runbook, the rollback plan, the purchase sheet you would actually buy from, and the first-build sequence for day one.

The short versionThe server is not ready to be bought yet, there is nothing for you to decide right now, and the work is carrying on in the meantime.

Why there is no date on this page

The remaining time is governed by one thing: whether the next independent review finds another real architecture flaw. If it does, that flaw is repaired and the architecture is reviewed again. If it does not, the server package can be frozen. Any number given before that answer exists would only be a guess dressed up as a plan, so none is given here.

03

Philosophy

The philosophy, area by area.

Eleven areas. Each one opens with the idea in a single line, then explains it. All of this is target design — the standard the moved system is being held to.

01

Trust and evidence

In one lineOne source of truth, raw evidence that is never edited, and a visible trail from every answer back to the facts it came from.

If you cannot trust the numbers, nothing built on top of them matters. So the foundation is boring on purpose: facts are recorded once, kept exactly as they arrived, and every conclusion can be traced back to them.

  • One canonical source of truth. If two places disagree about a fact, one of them is a copy, and the copy loses.
  • Raw evidence is immutable. Written once, never quietly edited, never overwritten to make a later result look better.
  • Every derived number carries its lineage — what it was built from, by which recipe, at what time. You can always walk backwards from an answer to the raw facts.
  • Nothing is silently rewritten, promoted or declared valid after the fact. A result that failed stays failed and stays visible.
  • Independent reviews must be repeatable later, after software has been upgraded, and reach the same answer from the same stored evidence.
02

Data intake and the engine

In one lineCapture each fact once, check it at the door, slow down politely when overloaded, and never let research work block the trading path.

The intake is the front door of the whole system. Everything downstream inherits whatever mistakes are made here, so the rules are strict and few.

  • Capture once. The live feed and the engine record each fact a single time, in one agreed shape.
  • Validate early. Bad or incomplete data is caught at the door, not discovered three steps later inside a result.
  • Backpressure when the door is crowded. When more arrives than can be handled, the system deliberately slows intake in a controlled way rather than silently dropping data or eating all the memory.
  • Stable contracts. The engine offers other parts of the system a fixed, documented way to ask for data, so those parts can change without the engine changing.
  • The hot path stays clear. The fast route that watches the market and could place a trade is never blocked by a research scan, a big historical read or an AI job.
03

Shared data and storage

In one lineStore raw data once; everything reads from one shared, versioned, analysis-ready copy — no experiment keeps a private year of history.

This is the single biggest difference between a system that grows and one that slowly strangles itself. Copies are the enemy: they cost disk, they cost memory, and worst of all they eventually disagree with each other.

  • Raw data is stored once. There is one copy of it in the system, and everything that needs it reads that copy.
  • One shared analysis-ready layer. Versioned and partitioned — organised so that asking for three days of one coin reads three days rather than the whole year.
  • Reusable feature tables. The expensive calculations everyone needs are computed once and shared, so no experiment has to work them out again.
  • Experiments hold receipts rather than data. An experiment keeps a small manifest naming the exact slice it used, so the run can be repeated later without a private copy existing anywhere.
  • Identical and overlapping work is coalesced. If two experiments want the same slice, it is prepared once and shared between them.
  • A training-ready snapshot is a manifest plus shared feature data — not another copy of a year of raw candles.

The trough testWith 50 experiments running and 35 of them needing chart data, all 35 drink from one shared trough. There are not 35 copies on disk, and there are not 35 copies in memory.

The same discipline is what makes the machine sizing honest. The 128 GB server should be able to run hot — busy, well used — while staying inside a deliberate safety reserve, rather than freezing or paging itself to death the first time several heavy jobs overlap.

  • Memory and disk-traffic quotas, so no single job can quietly consume the machine.
  • A bounded number of workers. Work queues rather than everything starting at once.
  • One shared cache rather than each job warming its own private one.
  • Backpressure applies here too — when the machine is full, new work waits its turn in a queue, which is what keeps the machine standing.
The performance and storage numbers this design is being held to

These are design targets used to size the machine and judge the layout. They are not measurements of a running system.

  • Find every coin that crossed a value thresholdAbout 2 seconds
  • Load 5,000 full coin charts from cold storageAbout 30 seconds
  • Sweep roughly 1.6 years of historyWithin 6 minutes
  • Expected chart storageAbout 38 GB per year, per retained version
04

Composable modules

In one lineEvery experiment says out loud which parts of the system it uses and which size of coin it covers.

The system is built from named parts. An experiment picks the parts it needs and labels them plainly, so anyone reading a result can see what went into it without asking. Several modules and several coin-size ranges can take part in a single experiment.

Module tags

Charts / OHLCV
Price and volume history, candle by candle.
Viewers / Phanes
Attention and ranking signals: who is watching, and how that changed.
Wallets / Holders
Who is buying, who is holding, how concentrated ownership is, and how that shifts.
KOLs
Presence and timing of accounts whose posts move attention.
Social / Grok
Wider social chatter and sentiment around a coin.
Execution
What a trade would really have cost: liquidity, slippage, fees, priority costs, failed fills.
Risk / Exit
Stops, time stops, invalidation, position size and exit behaviour.

Coin-stage labels

Stage labels are kept separate from module tags, and the actual numeric range in force is always printed next to the label, so the label never appears on its own. These are the ranges the design currently uses; whatever an experiment really runs with is shown on screen every time.

Birth
launch → $5kThe first minutes of life, when almost nothing is known yet.
Low Cap
$5k → $50kThe first real burst, and where most of the noise lives.
Mid Cap
$50k → $250kSurvived the first stage; behaviour starts to differ.
High Cap
$250k → <$50MDeeper liquidity, slower moves, different risks.

  • Modules have stable contracts — a fixed, documented way to ask them for data — so a new module can be added later without rewiring the whole Lab.
  • A result that used four modules says so on its face, and a result restricted to one cap range says that too.
05

The active Lab

In one lineThe Lab starts empty after the move; you describe an idea in ordinary words and approve a plain-English plan before anything runs.

The Lab is where questions become experiments, and you drive it by talking to it in ordinary words instead of filling in a form.

  • The active Lab starts empty and clean after the migration.
  • Existing experiments are preserved in a read-only archive. Readable forever, but not cluttering the active list.
  • You chat naturally with an AI. It turns that into a plain-English plan: what it will test, which modules it needs, which cap ranges, whether the data is ready, the likely runtime and honestly why it takes that long. Then it stops and waits for your approval.
  • Nothing heavy runs before you approve it.

Once running, the experiment page is meant to be readable at a glance: the real stages, real progress, what it is doing right now, how long is left, and how much of the machine it is using. When it finishes, it ends with a clear conclusion, a confidence level, the caveats that actually matter, and one or two suggested next steps — with an optional deeper section underneath for anyone who wants the underlying numbers.

  • Side discoveries become nested sub-experiments inside the parent page, not a swarm of near-duplicate experiment names in a list.
06

Scheduled work

In one linePermanent scheduled jobs are rare; experiment jobs are temporary, budgeted, and clean up after themselves.

A scheduled job is a task the machine runs by itself on a timer. They are useful and they are also how systems silently fill up with work nobody remembers starting. So they get a lifecycle: born for a reason, watched while alive, and removed when done.

  • Permanent schedules are rare and limited to health checks, security checks, backups, retention and genuinely necessary maintenance.
  • Experiment jobs are temporary and owned by the Lab. Each carries a purpose, an owner, the exact input snapshot it used, a resource budget, visible progress, an expiry date and automatic cleanup.
  • Finished work disappears from the active system. What remains is a tiny audit receipt and whatever output was actually useful.
  • Re-scanning gigabytes on a timer means something underneath is built wrong. The fix is partitions, indexes, incremental checkpoints and shared snapshots.
  • Before any new scheduled job is added, one question is asked: is this compensating for missing live streaming or missing indexing? If yes, the layer underneath gets fixed instead.
07

Research, timing, execution and risk

In one lineA pattern only becomes a strategy once entry, timing, stop, costs, exits and position size have all been tested against reality.

This is memecoin research, so it is judged on memecoin terms. Spotting a shape on a chart is the easy part and it is worth almost nothing on its own.

  • A pattern is not a strategy until entry, timing, a realistic stop, a time stop, an invalidation condition, costs, exits and position sizing have all been tested.
  • Vague words get defined from data. "Immediately" is not a feeling: it is the measured time-to-bounce and time-to-failure distributions for that exact coin stage and that exact market-cap range.
  • The stop that matters is the tightest one that survives reality — after noise, thin liquidity, latency, price impact, failed fills, fees and priority costs — not the tightest number that looks good on paper.
  • Results are judged on the right scoreboard: how much of the large moves was captured, how often the initial stake was recovered, net expected value after costs, drawdown, tail and rug losses, runners missed and time exposed. The annual-return framing borrowed from traditional finance does not describe this market, so it is not used here.
How every position is tested — the rules in full
  • Enter small. The first position is a probe, sized to find out whether the idea is working.
  • Add only on genuinely new confirming evidence — something that was not known when the position was opened.
  • Recover the initial stake as soon as it is sensible, so the remaining position is playing with winnings.
  • Take partial profit, then leave a runner for the 2x, 3x and 4x moves that make the whole exercise worthwhile.
  • Exit quickly when the thesis breaks. The invalidation condition is written down before entry, not argued about afterwards.
  • Martingale and naive averaging down are forbidden outright. Doubling into a losing position is refused by the rules, and any add at all requires remaining risk budget, acceptable execution conditions and a hard maximum total position.

A paper position can show a live confidence panel, split into parts anyone can read rather than one mysterious number: pattern, wallets and holders, viewers and momentum, social and KOL, execution and liquidity, risk warnings, and data freshness.

Those parts map to actions through fixed rules: deterministic thresholds, persistence (a signal must hold, not flicker for one second) and cooldowns (no reacting to the same thing twice). The available actions are hold, add cautiously, recover the initial stake, reduce, or exit. The score itself is calibrated against what actually happened in paper trading, so it earns its confidence rather than asserting it.

08

Machine learning and candle research

In one lineCandle questions are allowed, but only inside a matched group of similar coins, and only ever tested on the future.

Machine learning here means one thing: letting a model find patterns in past candles. It is genuinely useful and it is also the easiest place in the whole system to fool yourself, so the guard rails are strict.

  • Candle experiments can ask the obvious questions: after this pattern, what is the next candle most likely to do — and what about the next five?
  • Always separated by exact market-cap range, age since birth, liquidity and activity level. A $6k coin twenty minutes old is not the same animal as a $600k coin three days old, and averaging them produces a confident answer about nothing.
  • Future-only, walk-forward testing. The model learns on the past and is judged on data it has never seen, so it can never use information that would not have existed at the moment of the trade.
  • ML is one tool inside a reasoned experiment. It does not settle the question on its own, and it is no licence to generate a thousand slightly different parameter variants and call the pile of them research.
  • "No edge here" is a real result and gets recorded as one.
09

The AI-assisted idea factory

In one lineCheap scanners narrow the firehose; the AI reads summaries, asks one good question with a reason, and drafts one coherent experiment.

There is far too much market data for any AI to read, and reading it all would be both slow and pointless. So the shape is: dumb-and-cheap first, clever-and-expensive last.

  • Cheap, deterministic scanners reduce the firehose to a bounded list of genuinely unusual observations. The language model never reads every trade or every candle.
  • The AI receives compact summaries and representative samples, then asks an original, human-level question — with a stated reason why it is worth asking.
  • It checks for duplicates first, then drafts a single coherent parent experiment rather than five overlapping ones.
  • Parameter spam is rejected. Thirty near-identical threshold variants amount to one idea and twenty-nine wasted machine-hours, so they are refused before they run.
  • Follow-ups nest under the parent experiment.
  • Human approval comes first. Later, once proposals have earned trust, safe low-cost work may run automatically — with spending budgets and kill switches.
  • Creative thinking may use AI; arithmetic may not hide behind it. Execution and risk calculations stay reproducible and auditable, with no hidden AI-only reasoning behind a number.
10

Operations, health, security and visibility

In one lineServices run quietly and supervised, and anything long-running says what it is doing and whether it is stuck.

Most of the daily pain in the current setup has nothing to do with the algorithms. It comes from not knowing what is running, why it stopped, or whether something is wedged.

  • Services run hidden and supervised. No console windows flashing up on the desktop, no job that only survives because a window is open.
  • Health and security checks run continuously, and resource use is visible rather than guessed at.
  • Deployment is recoverable. A bad change can be rolled back without heroics.
  • Everything running has a clear owner and, where appropriate, an expiry date.
  • Every long-running action shows what it is doing, why it is doing it, and whether it is blocked, in enough detail that you can tell real progress from a job that has quietly stalled.
11

Expandability and the server move

In one lineNew parts join through documented contracts, and the server is bought only after the plan has been independently checked.

The design assumes it will be extended, because it will be. The cost of that assumption is paid once, up front, in discipline.

  • New modules and experiments join through contracts, not one-off glue code wired in by hand and remembered by nobody.
  • The server purchase follows a verified architecture, a capacity model, a migration runbook and a rollback plan. All four have to exist and hold up before any money is spent.
  • Olympus is preserved as a future compatibility concern. The design leaves room for it. Its implementation and validation come later, and it does not size this server.

04

Example days

What a working day should actually look like.

Seven walk-throughs. These are illustrative examples of how the finished system should feel to use — target design, not recordings of real runs. The times are there to show the order things happen in and the pace of a day.

A

An ordinary strategy conversation

The most common day. An idea arrives in your head in ordinary words and leaves the Lab as a tested answer.

  1. 09:05

    You say it plainly: I keep seeing coins stall around $25k and then run. Is that real, or am I remembering the ones that worked?

  2. 09:08

    The AI answers with a plan before any result exists: why the question is worth asking, the modules it needs — Charts / OHLCV Wallets / Holders Execution — the range it will use, Low Cap $5k → $50k, whether the data is already prepared, an estimated runtime and the honest reason it takes that long.

  3. 09:09

    It also lists the risk questions the experiment must answer before the idea could ever be traded: where the stop goes, what the time stop is, what costs apply, and what would prove the idea wrong.

  4. 09:10

    You read one page of plain English and approve. Nothing heavy ran before this point.

  5. 09:11

    The Lab starts. The page shows the current stage, what it is reading right now, how much is left and how much of the machine it is using.

  6. 10:40

    Result: a conclusion in plain words, a confidence level, the caveats that matter, and one suggested next step. Underneath, an optional section with the underlying numbers for when you want them.

B

A year-scale look back across every module

Take every coin that reached $10k and then $50k. Show me the full chart patterns, the wallets, the holders, the KOLs, the viewer signals and the Phanes rankings. The kind of question that used to mean days of preparation.

  1. 08:40

    The question is asked in one sentence.

  2. 08:41

    The cohort is found from a small index rather than by reading a year of raw data. It returns the coins that crossed both levels and the exact moment each crossing happened.

  3. 08:45

    The experiment declares itself: Charts / OHLCV Wallets / Holders KOLs Viewers / Phanes, moving from Low Cap $5k → $50k into Mid Cap $50k → $250k.

  4. 08:50

    Reads are partitioned: only the relevant coins and the relevant days are loaded, from the shared analysis-ready layer. Another experiment prepared part of that slice yesterday, so this one reuses the shared snapshot instead of building it again.

  5. 09:20

    Rankings and memberships are read as they were known at the time, so later knowledge cannot leak backwards into an old event and make the past look obvious.

  6. 10:15

    Two side questions appear during the run. Both become nested sub-experiments under this one. Neither gets its own copy of the year.

  7. 11:30

    Result delivered. The storage this whole day added comes to one manifest, some shared features and one write-up, with no extra copy of the year sitting anywhere.

C

A low-cap bounce and loss-minimisation day

A repeating shape shows up: birth, a burst to $5k–$10k, a pause, a dump, and occasionally a real recovery. Worth understanding, and dangerous to trade badly.

  1. 07:30

    A cheap scanner flags the shape as unusually frequent overnight and describes it in one line.

  2. 09:00

    The AI proposes a single experiment rather than ten: how long the bounce takes when it happens, how long failure takes when it does not, the smallest stop that survives real execution, a time stop for when nothing happens at all, exits triggered by warning factors, partial profit-taking, recovering the initial stake, leaving a runner, and adds allowed only on new evidence.

  3. 09:05

    Costs are built in from the start — fees, priority costs, slippage, failed fills — because a stop that only works without costs does not work.

  4. 09:15

    Approved. It runs as a paper monitor for the day. Every position is simulated; no real money is involved.

  5. 11:00

    The live confidence panel shows its parts separately: pattern, wallets and holders, viewers and momentum, social and KOL, execution and liquidity, risk warnings, data freshness.

  6. 13:20

    Thresholds and cooldowns turn those parts into one action: hold, add cautiously, recover initial, reduce, or exit. An add is refused because the risk budget is used up, even though confidence is high.

  7. 18:00

    End of day: what the smallest realistic stop actually was, what it cost in runners missed, and whether the recovery leg is worth trading at all.

D

A candle and machine-learning day

A narrow, technical question, kept honest by matching the group first and testing only on the future.

  1. 10:00

    The question: after this exact pattern, what is the next candle most likely to do — and what about the next five?

  2. 10:10

    The group is fixed before anything is trained: exact market-cap range, age since birth, liquidity band and activity level. Mixing those would produce a confident average of unrelated things.

  3. 10:30

    Training runs on the past only, and is scored walk-forward on stretches of data the model has never seen.

  4. 10:35

    The experiment states in advance what result would change a decision — for example: if failure inside the next five candles is more common than success in this group, entry waits for confirmation instead of anticipating it.

  5. 15:00

    The answer for this group is "no usable edge". That is recorded as a finding, with the group definition attached, so nobody spends another day rediscovering it.

E

A side-discovery day

The most valuable accidents happen mid-experiment. They need somewhere sensible to live.

  1. 11:40

    Halfway through a larger experiment, something odd appears: a small set of wallets shows up early in a suspicious share of the winners.

  2. 11:45

    It becomes a nested sub-experiment on the same page, with its own stages, its own progress and its own result.

  3. 14:00

    It finishes without disturbing the parent run.

  4. 16:30

    The parent conclusion keeps the relationship: it says where the side finding came from, and what it does — or does not — change about the main answer.

  5. 16:31

    What this arrangement avoids is a new top-level experiment with a nearly identical name, drifting away from the context that produced it.

F

A maintenance day

The boring day that decides whether the system is still healthy a year from now.

  1. 03:00

    Permanent scheduled work runs as usual: health checks, security checks, backups, retention.

  2. 09:00

    Three experiment schedules from last week reach their expiry and remove themselves. Their scratch data goes with them.

  3. 09:01

    What is left behind is deliberately small: a receipt saying what ran, on which input snapshot and what it produced — plus the outputs that were actually useful.

  4. 09:30

    The health view shows nothing running that nobody remembers starting, and no scratch pile quietly growing on a disk.

G

A future supervised idea-factory day

Later, once the proposals have proved themselves. Still supervised, still bounded.

  1. 02:00

    Scanners work through the night and produce a bounded list of unusual observations. The bound is deliberate, so what lands in the morning is a short list you can actually read.

  2. 08:30

    The AI proposes a small number of reasoned, genuinely new experiments, each with a stated reason for existing.

  3. 08:31

    Duplicates of existing work and formula spam are rejected before you ever see them.

  4. 09:00

    You read the short list and approve what runs. Automation of the cheap, safe end comes later still — and even then with spending budgets and kill switches.

05

Not in this gate

Deliberately not part of this decision.

Keeping the boundary sane is what stops the move from expanding forever. Each of these matters, and each one happens after this move rather than inside it.

Olympus
Later. The design leaves room for it as a future compatibility concern, but it will not delay this move and it will not size the first server.
Moving the dashboard interface
The dashboard stays on your PC for this cutover. Its data feeds must keep working; relocating the interface itself is not required.
Live-money trading
Not authorised. Everything remains paper-only until a separate, explicit decision and a safety gate.
Large historical backfill
The first large backfill follows the move. It is not a reason to postpone buying or building the server.

06

Rules

Rules we refuse to break.

If a proposal breaks one of these, the proposal changes — not the rule.

  1. No duplicated raw truth.One canonical copy of the facts. Everything else points at it.
  2. No experiment-owned copy of a shared year-scale dataset.An experiment keeps a receipt naming the slice it used, never its own private year of history.
  3. No unbounded scan on the live machine.Every read has limits, a budget and an owner. A job that wants to read everything gets rewritten until it no longer needs to.
  4. No orphan job, schedule or scratch output.Everything that starts has an owner and an end. Nothing survives because nobody remembered to stop it.
  5. No hidden AI-only rationale.If a number drives a decision, the reasoning behind it must be readable and reproducible by a human.
  6. No trade hypothesis without time, costs, exit and invalidation.A pattern with no stop, no clock and no cost model is still only an observation.
  7. No confidence-based add without new evidence and a hard risk budget.Feeling more sure about a position does not count as new information, and adding into a loser is forbidden outright.
  8. No server purchase before the specification, runbook and rollback are independently checked.The money is spent once the plan has survived review, and never as a way of forcing the plan to finish.

07

Words

Plain words for the unavoidable terms.

Everything on this page is written to be readable without these. They are here for the few terms that have no shorter honest substitute.

OHLCV
The five numbers that make up one candle on a price chart for a slice of time: open, high, low, close and volume.
Parquet
A file format for storing tables efficiently, arranged so a question can read just the days and columns it needs instead of the whole file.
Module
One self-contained part of the system — charts, wallets, viewers, social, execution, risk — with a fixed, documented way of being asked for data.
Manifest / snapshot
A receipt naming exactly which slice of data an experiment used, so the same run can be repeated later without keeping a private copy of the data.
Backpressure
When more data arrives than can be handled, the system deliberately slows the intake instead of dropping data silently or running out of memory.
Paper position
A simulated trade with no real money at risk, used to measure whether an idea would actually have worked.
KOL
"Key opinion leader" — an account whose posts move attention, and often price, when they mention a coin.
Runner
The small part of a position deliberately left open after profit has been taken, in case the coin keeps going 2x, 3x or 4x.
Time stop
An exit rule based on the clock rather than the price: if the expected move has not happened by a set time, leave anyway.
Nested sub-experiment
A smaller question that appeared during a bigger experiment and is answered inside it, on the same page, instead of becoming a separate experiment.
Cohort
A group of coins matched on the things that matter — size, age, liquidity, activity — so they can fairly be compared with each other.
Walk-forward testing
Training on the past and scoring only on later data the model has never seen, so a result cannot be flattered by information that did not exist at the time.
Hot path
The fast route that watches the market and could place a trade. It is kept clear of heavy research work on purpose.
